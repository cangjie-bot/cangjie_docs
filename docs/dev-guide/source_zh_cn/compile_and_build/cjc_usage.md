# `cjc` 使用

`cjc`是仓颉编程语言的编译命令，其提供了丰富的功能及对应的编译选项，本章将对基本使用方法进行介绍。

`cjc-frontend` （仓颉前端编译器）会随 `cjc` 一起通过 `Cangjie SDK` 提供，`cjc-frontend` 能够将仓颉源码编译至仓颉的中间表示 （`LLVM IR`）。 `cjc-frontend` 仅进行仓颉代码的前端编译，虽然 `cjc-frontend` 和 `cjc` 共享部分编译选项，但编译流程会在前端编译结束时中止。使用 `cjc` 时仓颉编译器会自动进行前端、后端的编译以及链接工作。`cjc-frontend` 仅作为前端编译器的实体体现提供，除编译器开发者外，仓颉代码的编译应优先使用 `cjc` 。

## `cjc` 基本使用方法

本节介绍 `cjc` 的基本使用方法。关于编译选项详情，请查阅 [cjc 编译选项](../Appendix/compile_options.md)章节。

`cjc` 的使用方式如下：

```shell
cjc [option] file...
```

假如有一个名为 `hello.cj` 的仓颉文件：

<!-- run -->

```cangjie
main() {
    println("Hello, World!")
}
```

可以使用以下命令来编译此文件：

```shell
$ cjc hello.cj
```

此时工作目录下会新增可执行文件 `main` ，`cjc` 默认会将给定源代码文件编译成可执行文件，并将可执行文件命名为 `main`。

以上为不给任何编译选项时 `cjc` 的默认行为，可以通过使用编译选项来控制 `cjc` 的行为，例如让 `cjc` 进行整包编译，又或者是指定输出文件的名字。

> **说明：**
>
> 在 Windows 平台上编译大型工程时，链接命令需携带所有目标文件与库文件的路径，或包含来自 `LIBRARY_PATH` 环境变量的超长参数，其长度可能超过 Windows 单条命令行长度上限，导致链接器无法启动。为避免该问题，当链接命令长度达到阈值时，`cjc` 会自动将链接参数写入响应文件（response file，供链接器从文件中读取参数，效果等同于在命令行中直接给出），并以 `@<文件路径>` 的形式调用链接器。使用 `--save-temps <目录>` 选项，响应文件将直接生成在指定目录且编译结束后保留，用于问题排查。使用 `-V` 选项编译，可从打印的链接器命令中看到响应文件路径（`@<文件路径>` 形式）。

## `cjc` 使用的链接器

`cjc` 完成后端编译后会调用链接器生成最终产物，不同目标平台使用的链接器如下：

| 目标平台 | 链接器 | 生效条件 | 链接器来源 |
| --- | --- | --- | --- |
| Linux | `ld` | 默认 | 系统链接器 |
| Linux | `ld.lld` | 使用 `--lto=[full\|thin]` 或启用硬件内存安全检测时 | 随 SDK 提供 |
| macOS / iOS | `ld64.lld` | 默认 | 随 SDK 提供 |
| Windows | `ld.lld` | 默认 | 随 SDK 提供 |
| OHOS | `ld.lld` | 默认 | 随 SDK 提供 |
| Android | `ld.lld` | 默认 | 随 SDK 提供 |

其中 `ld.lld` 与 `ld64.lld` 是 LLVM `lld` 的对应驱动，由 SDK 在 `$CANGJIE_HOME/third_party/llvm/bin` 目录下提供。

`--link-option` 与 `--link-options` 透传的参数会直接交给上述链接器处理，可用参数取决于链接器的种类，具体请查阅对应链接器的文档。
